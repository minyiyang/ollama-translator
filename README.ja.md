# Ollama Translator

[![CI](https://github.com/minyiyang/ollama-translator/actions/workflows/ci.yml/badge.svg)](https://github.com/minyiyang/ollama-translator/actions/workflows/ci.yml)
[![Python 3.11+](https://img.shields.io/badge/python-3.11%2B-blue.svg)](https://www.python.org/downloads/)
[![License: MIT](https://img.shields.io/badge/license-MIT-green.svg)](LICENSE)

[English](README.md) | [简体中文](README.zh-CN.md) | **日本語** | [Français](README.fr.md) | [Español](README.es.md) | [Deutsch](README.de.md) | [한국어](README.ko.md)

英語から中国語、中国語から英語への文芸翻訳を主な対象とした、ローカルで動作し、
中断しても再開できる書籍翻訳パイプラインです。EPUB、RTF、テキスト、Markdown、
HTML、Word（.docx）、テキストを含む PDF を入力として受け取り、翻訳を元と同じ形式で
返します。EPUB、PDF、Word、HTML、Markdown、テキストとして書き出すこともできます。
字幕ファイル（.srt、.vtt、.ass）にも対応しており、タイミングを保ったまま
字幕キュー単位で翻訳します。処理はすべてローカルの Ollama モデルで行い、
クラウド API も MCP サーバーも、LangGraph や AutoGen のようなエージェント
フレームワークも使いません。

英語から簡体字中国語（`en-zh`）とその逆（`zh-en`）は調整済みの言語ペアで、
すべてのチェック、用語集、スタイルシート、訳文の推敲が動作します。
フランス語（`fr`）、日本語（`ja`）、スペイン語（`es`）、ドイツ語（`de`）、
韓国語（`ko`）にはプロファイルがあり、句読点の慣習、呼称、数詞、プロンプトの
用例が、翻訳元・翻訳先のどちらの場合についても用意されています。それ以外の
言語は汎用ティアとして受け付け、その言語では実行できないチェックはスキップ
します（訳文の推敲も行いません）。言語ペアは設定ファイルで
`translation.direction: en>ja` のように指定し、言語コードは BCP 47 に従います。
英語・中国語以外のペアでは、翻訳品質はモデルに大きく左右されます。詳しくは
[docs/GENERIC_LANGUAGES.md](docs/GENERIC_LANGUAGES.md)（英語）を参照してください。

## 解決する問題

書籍 1 冊を翻訳するときの失敗の仕方は、モデルを 1 回呼び出すときとはまったく
異なります。LLM に章ごとにそのまま翻訳させると、たいてい次のような問題が起きます。

- **用語の揺れ**：同じ人名や地名が、第 3 章と第 20 章で別の訳になる。
- **構造の破損**：`<em>` や `<i>` などのインラインタグが書き換えの途中で失われ、
  EPUB を開くと組版が崩れている。
- **数量の誤り**：数値、単位、距離、時間が黙って書き換えられ、人の目では
  気づきにくい。
- **修復による劣化**：もともと正しかった文をモデルが「修復」し、良い訳文を
  悪い訳文に置き換えてしまう。
- **中断するとやり直し**：第 40 章でエラーになると、最初からやり直すしかない。

このプロジェクトでは、より長いプロンプトに頼るのではなく、これらの問題を
1 つずつ独立したステージに分け、それぞれにチェックポイントを設けて扱います。

## 処理の流れ

```text
decompile
  -> extract_glossary -> resolve_glossary -> approve_glossary
  -> build_story_context (optional)
  -> preprocess -> translate
  -> audit_translation -> audit_consistency -> repair_translation
  -> reprose_translation
  -> review_repaired -> repair_review -> validate_repaired
  -> translate_title -> compile -> validate_epub
```

各ステージは、成果物を `runs/<job-id>/` 以下のワークスペースにチェックポイント
として書き出します。`resume` を実行すると、完了して検証も通ったステージは
スキップされ、ジョブは最初からではなく、影響を受ける最も手前のステージから
再開します。

## 実行例：『不思議の国のアリス』

リポジトリに同梱している Project Gutenberg のサンプルで、英語から簡体字中国語
への翻訳を最初から最後まで実行できます。以下の手順はすべてローカルのブラウザ
ダッシュボードで行います。

```powershell
book-agent ui          # http://127.0.0.1:8765/
```

> ダッシュボードの UI がまだ変わり続けているため、スクリーンショットは省略
> しています。UI が安定したら撮り直します。

**1. 設定と開始。** 「ジョブ」ページには、すべてのジョブが 1 ページ 10 件ずつ
表示されます。*ジョブを追加* で指定するのは、原書（既知のファイルから選ぶ、
参照する、ドロップする）、設定ファイル名、ジョブ ID だけで、ジョブ ID の既定値は
設定ファイル名です。[`configs/demo-alice.yaml`](configs/demo-alice.yaml) のような
既存の設定ファイルはそのまま使われ、新しい名前を指定すると
`config.example.yaml` をひな形として作成されます。ジョブを開くと **設定** タブが
表示されます。*オプション* には変更することの多い設定（訳文のスタイル、役割ごとの
モデルとそのインストール状況 ✓/✗、用語集の承認方法、品質チェック、出力）が
まとまっており、*すべての設定* では全項目を型、範囲、既定値、リセットボタン
付きで確認でき、*YAML* ではファイルを直接編集できます。この 3 つは常に同期
されます。*検証* を押すと、設定ファイルを保存して検証し、ジョブをドライラン
したうえで、必要なモデルがすべてインストールされているかを Ollama に確認します。
ジョブのヘッダーにある *翻訳を開始* は、検証に通ったあと設定が変更されていない
間だけ押せます。実行中のヘッダーには、現在の LLM 呼び出しが終わってから止まる
*一時停止* と、すぐに止める *停止* があり、どちらの場合も *再開* で直近の
チェックポイントから続行できます。デモ用の設定は、ローカルにインストール済みの
モデルだけを使い、訳文の推敲と EPUB のクリーンアップを有効にし、用語集の承認を
LLM に任せています。同じジョブをターミナルから実行するには
`.\scripts\demo-alice.ps1` を使います（`-Resume` で再開）。

**2. 用語集の承認。** `workflow.llm_glossary_review: true` の場合、根拠があり、
信頼度が高く、競合のないエントリはそのまま承認され、残りは LLM レビュアーに
回されます。「用語集」ページには、承認された用語、LLM がレビューしたエントリ、
その理由、変更内容が表示されます。人によるレビューを選んだ場合は、ジョブが
ここで一時停止し、同じページがエディターになります。訳語、カテゴリ、メモ、
別名を修正する、エントリを除外する、要確認のエントリ（一般語、訳語の重複、
低信頼度、根拠なし）だけに絞り込む、用語ごとに原文の用例を読む、といった操作が
できます。自分で直した版をそのまま承認することも、それ（または手を加えていない
ドラフト）を LLM レビュアーに渡すこともでき、どちらの場合もパイプラインは
自動的に再開します。

**3. 翻訳、監査、修復。** 「進行状況」ページは、ジョブをダッシュボードから
開始したかターミナルから開始したかにかかわらず、リアルタイムで追跡します。
各ステージの状態、予定されている LLM タスク数、現在の処理単位、呼び出し回数、
出力トークン数、所要時間に加えて、実行中のモデル呼び出しとセッションログが
表示されます。このサンプルでは、パイプラインが自力では確認できなかった
3 つのセグメントを残して、コンパイルの前で一時停止します。

**4. 最終レビュー。** 「最終レビュー」ページ（`book-agent review-ui
.\runs\demo-alice-en-zh` で直接開くこともできます）で、このレビューキューを
処理します。セグメントごとに、前後の文脈を含む原文、指摘（クリックすると
引用箇所がハイライトされます）、パイプラインの各段階の訳文、そして差分を
リアルタイムに表示するエディターが並びます。エディターは `resolve-review` と
同じ決定的なチェックを行います。判定を適用するとドラフトが承認され、続いて
EPUB のコンパイルと検証が行われます。レビューキューが空のまま承認待ちに
なっているドラフトは、同じページの **最終ドラフトを承認** で承認できます。

**5. 全文を読んで編集する。** **本文** タブには、すべての章が原文と訳文の
対になった行として表示されます。どのセグメントもその場で編集でき、理由の入力が
必要で、同じ決定的なチェックと差分表示が適用されます。最終レビューでの判定を
含め、すべての変更は 1 つの編集ログに記録され、再実行しても消えないので、
元に戻すことも履歴を確認することもできます。再実行によって編集済みセグメントの
訳文が変わった場合、そのセグメントは競合になり、どちらを採るかを自分で決めます。
*再コンパイル* を押せば、編集を反映した書籍を数秒で作り直せます。
**⤓ XLIFF をエクスポート** で書籍を CAT ツールに渡し、**⤒ XLIFF をインポート**
で翻訳者から戻ってきたファイルを、プレビューで確認してから取り込みます。

## 設計方針

- **機械的に検証できる構造は、モデルではなくコードで扱う**：EPUB の構造、
  インラインマーカー、各種識別子は決定的なコードで処理し、モデルには任せません。
- **確信のない修復より、見送りを選ぶ**：検証に通らなかった修復は破棄し、
  既存のより良い訳文を上書きさせません。そのセグメントは人によるレビューに
  回します。
- **リトライには上限がある**：検証結果が収束しなくなったらモデルの呼び出しを
  やめ、同じ失敗を繰り返しません。
- **汎用的な対処だけを行う**：失敗は種類ごとに汎用的なルールで扱い、特定の本や
  特定の箇所に向けたパッチをコードに埋め込みません。
- **コンテキストは必要な分だけ確保する**：設定の 131K は上限であり、毎回確保
  する量ではありません。通常のリクエストは 16K から、個別の修復と修復の検証は
  8K から始め、必要な場合にだけ 16K / 32K / 64K / 131K と段階的に広げることで、
  GPU メモリの使用量をリクエストの大きさに見合ったものにします。

## クイックスタート

### 1. Ollama とモデルを用意する

ローカルで Ollama が起動していることを確認し、設定で使うモデルを取得します。

```powershell
ollama pull qwen3.8:latest
ollama pull gemma4:31b
```

モデルを呼び出す最初のステージの前に、CLI がモデル名と設定されたコンテキスト
容量を確認します。

### 2. インストール

```powershell
python -m pip install -e .
book-agent --version
```

requirements ファイルからインストールすることもできます（依存関係の定義は
`pyproject.toml` が正です）。

```powershell
python -m pip install -r requirements.txt
python -m book_agent --version
```

Python 3.11 以上と `ollama>=0.6.2` が必要です。

### 3. 設定ファイルをコピーして確認する

```powershell
copy config.example.yaml my-book.yaml
book-agent config --file .\my-book.yaml
```

`config.example.yaml` は、実運用を想定した控えめな出発点であり、既定値の一覧では
ありません。いくつかの値は、意図的にコードの既定値と変えてあります。キーは
すべて省略でき、省略した場合は `book_agent/config.py` の既定値が使われます。

### 4. ドライランのあとで本実行する

ドライランはファイルを一切書き込まず、Ollama にも接続しません。

```powershell
book-agent run "D:\books\source.epub" --config .\my-book.yaml --dry-run
```

問題がなければ本実行します。

```powershell
book-agent run "D:\books\source.epub" --config .\my-book.yaml --job-id "my-book-en-zh"
```

コマンドはワークスペースのパスを表示します。以降のコマンドはすべてこの
ディレクトリを対象にするので、控えておいてください。RTF など EPUB 以外の入力も、
同じコマンドと同じパイプラインで処理します。

### 5. 状態の確認と再開

```powershell
book-agent status .\runs\my-book-en-zh
book-agent resume .\runs\my-book-en-zh --plain
```

`--plain` はログに書き出しやすい出力にするだけで、パイプラインの動作は
変わりません。

## モデルの役割分担

既定の分担は控えめに設定してあり、モデルはステージごとに個別に指定できます。

| タスク | 既定のモデル |
|---|---|
| 用語集の候補抽出 | `qwen3.8:27b` |
| 用語の解決とレビュー | `qwen3.8:latest` |
| 初訳と個別の修復 | `qwen3.8:latest` |
| 意味の監査 | `gemma4:31b` |
| 数量の検証と裁定 | `gemma4:26b`（必要に応じて `gemma4:31b` に切り替え） |
| 修復の比較と範囲を限った検証 | `gemma4:26b` |
| 推敲案の作成 | `qwen3.8:latest` |
| 推敲の検証 | `gemma4:31b` |

構造化 JSON を返す監査と検証の呼び出しでは、既定で thinking を無効にしています。
品質の向上が実測で確認できた場合を除き、有効にすることはおすすめしません。

## レビューと再開

既定では `require_glossary_review: true` で、用語集のドラフトを作成したところで
一時停止し、人による確認を待ちます。

```powershell
book-agent approve "D:\runs\my-job" --glossary "D:\reviews\glossary.txt" --resume
```

スキーマで制約したモデルによるレビューに切り替えて、そのまま続行することも
できます。

```powershell
book-agent approve "D:\runs\my-job" --llm-glossary --resume
```

レビュアーはエントリを修正または削除できますが、原文側の用語を新たに作り出す
ことはできません。プロンプトとモデルのハッシュ、試行回数、レビューモード、
成果物が記録されます。

### ブラウザダッシュボード

`book-agent ui` は、ループバックアドレスだけで待ち受けるダッシュボードを起動
します（オプション：`--runs`、`--configs`、`--port`、`--no-browser`）。上記の
コマンドと同じレビューゲートを扱えます。

インターフェースは英語、簡体字中国語、日本語、フランス語、スペイン語、ドイツ語、
韓国語で表示できます。いずれもパイプラインがプロファイルを持つ言語です。
ヘッダー右側のメニューから選択でき、選択はブラウザに保存されます。既定は英語
です。表示言語はジョブの翻訳方向とは無関係です
（[ダッシュボードのローカライズ](docs/LOCALIZATION.md)、英語）。

- **ジョブ**：ジョブを翻訳方向（例：`EN → ZH`）とともに一覧表示し、新しいジョブを
  作成します。完了したジョブには、一覧とジョブのヘッダーの両方に **ダウンロード**
  ボタンがあり、その横に形式のメニューがあります。メニューはジョブが返す形式
  （設定の `output.format`。既定では入力ファイルと同じ形式）から始まります。
  書籍は EPUB、PDF、Word、HTML、Markdown、テキストで、字幕ジョブは SRT、WebVTT、
  ASS でダウンロードできます。ファイル本来の形式以外の字幕形式を選ぶと、
  引き継がれないものがダッシュボードに表示されます。開始済みのジョブの設定は、
  *ロックを解除して編集* を押すまで読み取り専用です（実行中は解除できません）。
  解除すると、各変更がパイプラインに与える影響が表示され、最初に影響を受ける
  ステージからの再実行とともに保存されます。ジョブの **設定** タブでは、編集、検証、開始を行います。
  *言語* の設定には任意の 2 つの言語コードを指定でき、汎用ティアのペアでは
  スキップされるチェックが表示されます。**シリーズ** は、バージョン管理された
  シリーズ用語集を共有するジョブをまとめます。ヘッダーからは、一時停止（現在の
  LLM 呼び出しが終わってから）、停止、再開ができます。ターミナルから開始した
  ジョブも `book-agent pause <workspace>` で同じように一時停止できます。
- **進行状況**：`state.sqlite3` とセッションログをもとに、`--runs` 以下の任意の
  ジョブを追跡します。失敗または一時停止したステージは **再開**（完了済みの
  作業は保持）か **再実行** ができ、完了したステージは **ここから再実行**
  できます。再実行（`retry --stage X --resume`）の前には、やり直しになる
  ステージと失われる内容が確認ダイアログに表示されます。「最終変更」列には、
  各ステージに最後に起きた状態の変化（開始、完了、失敗、停止、一時停止、
  レビュー待ち、リセット）とその時刻が表示されます。
- **用語集**：一時停止中の用語集を編集して承認するか、LLM レビュアーに渡します
  （`approve --glossary` / `--llm-glossary` に相当）。
- **本文**：書籍を章ごとに、原文と訳文の対になった行として表示します。要確認、
  レビューキュー内、編集済み、競合のセグメントに絞り込めます。
  `validate_repaired` が完了すると、どのセグメントもその場で編集できます。
  保存には理由の入力が必要で、同じ決定的なチェックを通します（構造やマーカーの
  破損、空の訳文、未翻訳、重複、句読点の誤りは保存できず、その他の指摘は
  理由を入力すれば保存できます）。編集は `edits/segment-edits.jsonl` に記録
  されます。これはどのステージにも属さない追記専用のログで、再実行しても
  消えません。コンパイル時に検証済みのドラフトの上に適用され、編集が書籍より
  新しい場合は **再コンパイル** で作り直せます。再実行によって編集済み
  セグメントの訳文が変わると、そのセグメントは競合になり、自分の編集を残すか
  新しい訳文を採用するかを決めるまでコンパイルできません。各編集には履歴が
  あり、元に戻せます。**⤓ XLIFF をエクスポート** は書籍を XLIFF 2.1 として
  ダウンロードします。**⤒ XLIFF をインポート** は翻訳済みのファイルを
  セグメント単位でプレビューし（ユニット ID が一致し、原文が変わっていない
  ものだけを対応付けます）、確認したものだけを 1 つの理由を付けた編集として
  書き込みます（[XLIFF のインポート](docs/XLIFF_IMPORT.md)、英語）。
- **最終レビュー**：`resolve-review` と同じ検証で、人によるレビューキューを
  処理します。現在の訳文を受け入れるには、定型の理由を選ぶか、理由を自分で
  入力する必要があります。判定は「本文」タブでの編集と同じ編集ログに書き込まれ、
  レビューキュー内のセグメントを「本文」タブで編集した場合も処理済みに
  なります。未判定のセグメント数が
  `workflow.compile_max_unresolved_review_segments` 以下になると、判定済みの
  ものを適用して最終ドラフトを承認するかどうかを尋ねます。
  `book-agent review-ui <workspace>` でこのページを直接開けます。

ダッシュボードで予期しないエラーが起きた場合は、空白のページではなく、
エラーメッセージ、技術的な詳細、**再読み込み** ボタンを備えたバナーが表示
されます。

編集の記録はコマンドラインでも確認でき、XLIFF 2.1 としてエクスポートできます。

```powershell
book-agent edits "D:\runs\my-job"
book-agent edits "D:\runs\my-job" --export xliff --output my-job.xlf
```

パイプラインの `audit_consistency` ステージ（既定で有効、モデルは呼び出しません）
は、書籍全体の一貫性をチェックします。繰り返し現れる文やせりふはどこでも同じ
訳になっていなければならず、句読点はその本自身の慣習に従っていなければ
なりません。不一致は修復ステージに回され、修復できなかったものは
レビューキューに入ります。さらに `consistency.style_sheet.enabled: true` を
設定すると、用語集と同時に書籍の **スタイルシート**（繰り返し現れる表現と、
登場人物ごとのメモ）を抽出します。スタイルシートは用語集と同じレビューゲートで
人が確認します（「用語集」タブの「スタイルシート」セクション、または
`approve --style FILE`）。これは用語集を LLM にレビューさせる場合でも同じです。
繰り返し現れる表現は書籍全体で同じ訳になります。登場人物のメモは参考情報に
とどまり、代名詞や呼びかけの使い分けは原文の表現と場面によって決まります。
`consistency.story_context.enabled: true` を設定すると、省略可能な
`build_story_context` ステージが有効になります。章ごとに短い要約を作成し
（1 章あたり約 6 秒）、翻訳時の各チャンクに「これまでのあらすじ」を参考情報
として渡します。あらすじ自体は翻訳されません。
詳しくは [書籍全体の一貫性](docs/BOOK_CONSISTENCY.md)（英語）を参照してください。

ダッシュボードから始めた処理は、通常の CLI を子プロセスとして実行します。
そのためログとチェックポイントはターミナルから実行した場合と同じで、
ダッシュボードを閉じてもジョブは続行します。

ダッシュボードのフロントエンドは `frontend/` にあります（React + TypeScript）。
ビルド済みの成果物は `book_agent/web/static/` にコミットしてあるので、
パッケージのインストールに Node.js は必要ありません。UI を変更する場合は
次のようにします（Node 24）。

```powershell
cd frontend
npm ci
npm run dev      # ホットリロードで開発。/api は起動中の `book-agent ui` にプロキシ
npm test         # ヘルパーの単体テストとコンポーネントテスト（jsdom + Testing Library）
npm run build    # 型チェックして book_agent/web/static を再生成。結果もコミットする
```

## 終了コード

| 終了コード | 意味 |
|---:|---|
| `0` | コマンドが成功した、またはワークフローが完了した |
| `1` | 検証、設定、モデル、ステージ、または実行時の失敗 |
| `2` | ワークフローがレビューゲートで一時停止した |
| `130` | ユーザーによるキャンセル、またはモデル生成の協調的な中断 |

## テスト

テストスイートはオフラインで動作し、ローカルのモデルがなくても実行できます。

```powershell
python -m pip install -e ".[dev]"
python -m pytest
```
